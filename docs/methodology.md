# 测评方法论

## 1. 测评目标

本项目希望判断模型能否在不同任务形态下完成真实目标，而不只是生成一段语言上通顺的回答。题库因此覆盖四个相互补充的方面：

1. 推理：理解条件、计算、判断和解释。
2. Coding：交付可以运行和验证的程序。
3. 多模态：从图片中提取信息并完成判断。
4. Agent：调用工具、维护状态并完成多步骤事务。

四类题目属于同一套统一题库。当前范围和版本由 `benchmark/question_bank/manifest.json` 统一管理。

## 2. 题目设计

每道题在进入正式测评前，都应明确：

- 模型要完成的目标；
- 可用的信息和工具；
- 不能违反的约束；
- 可以被外部观察或复核的结果；
- 评分项、分值和严重错误边界。

题目优先选择容易理解但不容易靠模板蒙对的任务。对于涉及资金、权限、隐私、外部承诺、受保护对象和停止指令的场景，必须写出负向要求，例如“不执行退款”“不修改原文件”或“收到停止指令后立即停止外部动作”。

## 3. 从题面到结果

一次完整测评按以下顺序进行：

1. 从统一题库选择题目和版本。
2. 使用题目规定的素材、初始状态和请求条件。
3. 执行模型并保存原始请求与响应。
4. 根据题型收集答案、代码、图片分析、工具过程或最终状态。
5. 使用确定性检查、黑盒测试、状态断言和人工评分完成评审。
6. 保存逐项评分、失败原因、错误信息和复现所需的运行记录。

单轮题目通常一次发送一道题；Agent 题则需要工具执行器把模型动作应用到模拟环境，并把工具结果返回给模型，形成多轮闭环。

## 4. 四类能力的证据

| 能力 | 主要输入 | 主要证据 |
| --- | --- | --- |
| 推理 | 文字题面和约束 | 最终答案、推导过程、结构化字段或确定性核对 |
| Coding | 需求、初始代码或项目约束 | 可运行结果、黑盒测试、项目级检查和人工结果卡 |
| 多模态 | 固定图片和问题 | 关键文字、位置、数量、关系和不确定性表达 |
| Agent | 场景、工具、初始状态和用户指令 | 工具调用、工具返回、环境变化、最终状态和断言结果 |

Agent 题不能只把工具使用要求改写成文字题面后再看最终回答；没有工具执行和状态变化，就只能解释为规划或文本推理。

## 5. 题库更新

题库会根据预跑结果滚动更新。更新时需要保留：

- 题目版本和变更原因；
- 旧题面及其结果；
- 评分规则变化；
- 题目区分度、稳定性和失败原因；
- 哪些结论来自本地公开题目，哪些结论仍需人工确认。

旧版本保存在 `benchmark/question_bank/archive/`，不能和当前快照混用。
