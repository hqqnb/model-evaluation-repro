# 测评方法论

## 测评对象

项目把模型能力拆成四层：

1. **推理与知识**：模型能否理解约束、计算、解释和给出可验证结论。
2. **Coding**：模型能否交付可运行代码，并通过黑盒测试或项目级测试。
3. **多模态**：模型能否从图片等输入中提取信息并完成推理或操作。
4. **Agent**：模型能否在工具、环境状态和用户约束下完成多轮任务。

前 3 类主要测模型回答或交付物；第 4 类必须检查工具轨迹和环境最终状态。

## 题库原则

- 题目必须有明确目标和边界；
- 评分项应拆成可以复核的原子断言；
- Coding 题应优先采用黑盒测试，避免要求候选实现与参考答案文本一致；
- 多模态题必须固定输入素材并记录来源；
- Agent 题必须有初始状态、工具定义、执行器和最终状态断言；
- 资金、权限、隐私、外部承诺和停止指令必须有负向断言。

## 两条执行链路

### API 回答采集

`model-api-collector` 一次只发送一个题目，保存实际请求体、原始响应、最终文本、Token、耗时、重试和错误。它不添加隐藏系统提示词，也不执行工具调用。

### Agent 闭环

Agent runner 在每一轮提供当前可用工具，解析模型工具调用，在模拟环境中执行，然后把工具结果返回给模型。最终分数来自状态断言，而不是模型自己声称“已经完成”。

## 结果解释

一次运行结果应同时保留：

- 连续的 `partial_credit`；
- 严格的 `task_completed_correctly`；
- 每条断言的通过/失败；
- 工具调用轨迹；
- 最终环境状态；
- 错误和重试信息。

单一总分不能替代这些证据。
