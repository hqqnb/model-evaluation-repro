# 评分说明

## 通用原则

每道题都按照自己的评分项评分，题目中的分值、重要条件和严重错误边界优先于模型的自我描述。评分尽量拆成可以复核的原子要求，避免“整体感觉不错”成为唯一依据。

推理题可以使用确定性答案和参考检查；Coding 题优先运行黑盒测试或项目级测试；多模态题使用固定素材和题目评分标准；Agent 题检查工具轨迹和最终环境状态。

## Agent 评分

Agent 题同时保留：

- `partial_credit`：已经通过的评分要求占全部评分要求的比例；
- `task_completed_correctly`：所有要求都通过时才为 1；
- `assertion_results`：逐条要求的通过或失败；
- `trajectory`：工具调用和工具返回；
- `final_state`：环境最终状态；
- `hard_fail`：是否触发资金、权限、隐私、外部通知、受保护对象或停止指令相关的严重错误。

在 100 分制题目中，逐项分值应映射到原子要求；不能用一个没有权重的总断言代替整道题的评分规则。

## 如何看分数

分数应与证据一起阅读：

1. 总分说明完成程度；
2. 逐项评分说明缺口在哪里；
3. 运行结果说明失败来自模型、执行器还是上游服务；
4. 多次运行说明结果是否稳定；
5. 题库版本和请求参数说明不同模型结果是否可直接比较。

本地题库上的分数不是官方 held-out benchmark 分数，也不能把 API 失败直接当作模型能力失败。
