# 项目架构

项目的基本关系是：

```text
统一题库
  ├── 题目、素材、评分规则
  ├── Coding 检查和 Agent 场景说明
  └── 版本与来源清单
          ↓
执行入口
  ├── 单轮 API 回答采集
  └── Agent 多轮工具执行
          ↓
证据与评分
  ├── 原始回答和交付物
  ├── 测试结果和人工评审
  ├── 工具轨迹和最终状态
  └── 结构化报告
```

## 统一题库

`benchmark/question_bank/manifest.json` 是当前题库的唯一总入口。它把 20 道单轮题和 8 道 Agent 题放在同一版本下管理，并说明每道题的材料在哪里。

- `single_turn/`：保存推理、Coding、多模态题的实际输入、评分和素材。
- `agent/`：保存 Agent 场景、目标终态、评分规则和执行适配说明。
- `archive/`：保存旧版本、候选题、实验记录和来源材料。

目录的差异表示任务形态或材料形态，不表示存在多套互不相关的 benchmark。

## 执行入口

- `runners/model-api-collector/` 负责一次请求式的回答采集，保存实际请求、原始响应、最终回答、耗时、Token 和错误。
- `third_party/automationbench/` 提供可重置的模拟环境和工具执行底座，用于需要多轮交互的 Agent 题。
- `scripts/` 负责本地校验、初始化和统一运行入口。

API 只是模型与评测环境之间的传输方式。只有在工具被执行、环境发生变化、后续结果返回给模型并最终接受状态检查时，才可以把结果解释为完整 Agent 测评。

## 评分与结果

`evaluation/` 保存统一结果格式、评分器和报告。结果必须保留原始证据，不能只保存一个总分。内部答案、评分规则和敏感材料不进入模型输入。
