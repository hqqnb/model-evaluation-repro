# 模型测评工作总览

## 1. 项目目标

这项工作最终形成了一套从题目设计到结果发布的模型测评链路。核心问题不是“模型能不能写出一段看起来合理的回答”，而是：

> 模型面对真实任务时，能否理解约束、调用正确工具、改变正确状态、完成交付，并在失败后恢复。

因此，项目把测评拆成两类：

- 单轮 API 测评：采集推理、Coding 和多模态题目的原始回答。
- 多轮 Agent 测评：在受控模拟环境中执行工具调用，并根据环境状态和断言评分。

## 3. 题库和评分体系

统一题库共 28 道：

- 推理：8 道；
- Coding：8 道；
- 多模态：4 道；
- Agent：8 道，编号 T01-T08。

Agent 题目的共同评分结构是：

- 核心目标完成；
- 关键要求满足；
- 执行完整性；
- 风险与约束遵循。

题目不会只看最终自然语言回复，还会检查：

- 是否读取了正确事实；
- 是否调用了正确工具；
- 是否发生了必要的状态变化；
- 是否重复创建对象；
- 是否在中断或报错后正确恢复；
- 是否泄露隐藏判定字段或敏感信息；
- 是否完成了文件、记录或任务等最终交付。

## 4. 两条评测链路的边界

### 4.1 单轮 API 采集

`model-api-collector` 负责：

- 从 JSONL 读取题面；
- 向模型 API 发起请求；
- 保存原始响应、最终文本、推理内容、Token、耗时和错误；
- 记录 Provider、模型和请求元数据。

它不负责：

- 执行模型返回的工具调用；
- 把工具结果回传给模型；
- 维护业务状态；
- 根据环境状态进行断言评分。

因此，单轮采集适合回答质量、推理、Coding 和多模态交付的采集，不应把它的结果解释成完整 Agent 能力。

### 4.2 AutomationBench Agent 闭环

定制后的 AutomationBench 运行器完成以下闭环：

1. 加载任务和初始世界状态；
2. 向模型提供受限工具集；
3. 通过 Chat Completions、Responses 或兼容协议调用模型；
4. 解析模型工具调用；
5. 执行工具并返回工具结果；
6. 维护业务记录、文件和任务状态；
7. 直到模型结束或达到步数上限；
8. 根据断言、最终状态和工具轨迹计算部分得分、严格通过和技术失败。

这条链路测量的是实际工具编排和任务交付，不是“模型会不会描述工具调用”。

## 5. Agent 环境和工具建设

### Banking

为 T07 提供身份验证、转账查询、政策查询、审核申请和限额调整等操作。敏感操作需要先完成身份验证；不满足条件的动作会记录越权尝试，但不会把隐藏的正确判断直接返回给模型。

### Agentic workspace

为 T04、T05 等需要生成文件和分析交付物的任务提供受限工作区，支持文件列表、读取、写入、artifact 登记、结构检查和 finalize。工作区限制路径穿越，评分器检查文件是否存在、非空、结构有效、大小一致和内容是否符合任务要求。

### Benchmark task domain

将 T01-T08 注册为可运行任务，并把题目要求拆成初始状态、可见事实、允许工具、状态变化、错误记录和评分断言。

## 6. 评测完整性改进

这一轮迭代重点处理了以下问题：

- 模型不能从工具返回值中直接看到 `expected_*`、隐藏 oracle 或标准答案标签；
- 非法动作不能被静默吞掉，必须留下可评分的尝试轨迹；
- 银行业务敏感操作需要先验证身份；
- T03、T05、T06、T08 增加结构化交付物、动作顺序和恢复逻辑断言；
- T05 的不同文件覆盖和重复读取被单独计数；
- 工具结果减少重复状态和隐藏字段；
- 运行器记录工具调用数、模型轮数、Token、耗时、技术失败和重试次数。

相关实施计划保留在 [`docs/plans/agent-benchmark/`](plans/agent-benchmark/)。

## 7. 结果和证据

### 7.1 正式总分

`evaluation/agent/formal_scores_20260815.json` 是项目当前采用的正式总分登记文件。它来自人工确认后的 Agent 汇总，仓库内的排名或对外汇总应读取其中的 `official_score`，不能临时把题目级复核分重新求和。

### 7.2 最终批次

`agent-suite-v1.1-tool-errors-noleak-20260815` 是最终完整批次之一，记录：

- 8 道任务；
- 模型预检状态；
- 每个模型的有效任务数和技术失败数；
- 平均加权分；
- 严格通过率；
- 技术失败和异常原因。

该文件用于解释一次具体批次，不替代正式总分登记。

### 7.3 交互证据

`evaluation/agent/evidence/20260814-agent/` 保存 8 道题、10 个模型的 80 份交互回答。每份记录包含最终回复、工具调用过程和人工复核要点，轨迹中的 API Key、Bearer Token 和其他密钥已脱敏。

### 7.4 人工复核

`evaluation/agent/reviews/20260815-corrected/` 保存修正后的结构化复核材料，用来支撑模型级评分和问题归因。它不是新的题库版本，也不是另一套正式分数。

## 8. 结果解读边界

- `partial_credit` 不等于严格完成；
- 技术失败不等于模型能力失败；
- 模型文本不等于工具轨迹；
- 请求参数不一定等于上游实际使用的参数；
- 本地公开题目分数不等于官方隐藏集成绩；
- 不能把 OpenRouter 等平台的可观测数据直接表述为全市场份额；
- 题目中环境或评分器的限制需要与模型本身的错误分开记录。

## 9. 归档策略

本仓库采用“一个模块一份当前实现”的策略：

- 当前有效代码直接放在主目录；
- 版本变化通过 Git 提交记录保留；
- 最终结果和必要复核证据放在 `evaluation/`；
- 设计计划放在 `docs/plans/`；
- 发布工具放在 `tools/`；
- 临时运行输出、缓存、虚拟环境、浏览器状态、备份快照和失败探针不进入正式归档。

## 10. 当前仍需注意的事项

- Agent 测评依赖上游模型服务和当前 API 协议，重新运行时结果可能因模型、服务商、额度和接口行为变化而漂移。
- 旧批次和正式总分属于不同统计口径，新增批次不能直接覆盖正式总分文件。
- 结果发布工具中仍保留部分面向本地知识库的脚本，它们的输入路径和认证方式需要在具体环境中重新配置。
- 公开 GitHub 只应提交脱敏后的题面、代码、结果摘要和证据，不应提交任何本地密钥或登录态。
