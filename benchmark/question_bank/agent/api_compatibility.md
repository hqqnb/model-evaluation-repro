# Agent 题库 API 评估兼容性检查

## 一、结论

当前题库不能直接全部接入现有的 `model-api-collector` 运行。这个采集器只负责向模型发起一次请求并保存最终响应，没有执行工具、回传工具结果、维护环境状态或进行多轮 Agent 循环的能力。

项目中另有一条独立的 AutomationBench 评估链路，能够通过 API 调用模型，并在模型与模拟环境之间执行多轮工具交互。因此，正确的结论是：

| 使用方式 | 能否测真实 Agent 能力 |
| --- | --- |
| 只使用 `model-api-collector` | 不能 |
| 使用现有 AutomationBench 运行器和已有任务 | 可以 |
| 将当前 8 道题原样放入 AutomationBench | 不能全部直接运行 |
| 为缺少环境的题目补充工具、状态和断言后再接入 | 可以 |

如果只是把题面发给模型，让模型在最终回答中写出“应该调用哪些工具”，测到的是任务规划或文本推理，不是完整的 Agent 执行能力。

本次已进一步从 `τ³-Banking` 和 GDPval-AA v2 的评测方式中抽取两组工具底座，接入现有 AutomationBench：一组用于银行业务查询、验证和审核申请，一组用于受限工作区内的数据处理与交付物检查。接入后，相关题目不再只能依赖模型“描述自己会怎么做”，而是可以实际调用工具、改变环境状态并接受断言评分。

## 二、现有两条链路

### 1. `model-api-collector`

该采集器的定位是模型 API 原始回答采集：

- 根据 JSONL 中的题面构造一次 `messages` 或 `input` 请求；
- 将请求发送到 OneAPI；
- 保存原始响应、最终文本、推理内容、Token、耗时和错误；
- 不启动工具执行器，不维护业务状态，不把工具结果回传给模型。

需要注意的是，配置层面理论上可以手工把 `tools` 字段塞进请求参数，但这最多只能让模型返回一次工具调用。采集器不会执行这个调用，也不会发起下一轮带有工具结果的请求，所以不能形成完整 Agent 轨迹。

### 2. AutomationBench 运行器

AutomationBench 的运行方式符合 Agent 测评的基本闭环：

1. 从任务配置加载初始业务状态；
2. 根据题目配置向模型提供可用工具；
3. 通过 Chat Completions、Responses 或 Anthropic API 调用模型；
4. 解析模型返回的工具调用；
5. 在模拟环境中执行工具并返回工具结果；
6. 重复多轮，直到模型结束或达到步数上限；
7. 根据最终环境状态检查断言；
8. 保存完整工具轨迹、最终状态、断言结果、耗时和 Token。

因此，API 只是模型与评估环境之间的传输方式。真正让它成为 Agent 测评的，是“工具定义 + 工具执行器 + 状态变化 + 断言评分”这套外部闭环。

## 三、实际可运行性检查

本次检查已完成以下验证：

- AutomationBench 的本地依赖环境可用；
- AutomationBench 全量测试套件通过：`1416 passed`；
- 新增 benchmark 专项测试 `17 passed`，覆盖工具注册、状态变化、API 路由、任务注册和部分得分；
- 已接入 `banking` 状态环境及 8 个银行工具，可通过 direct-tool 或 `api_search` + `api_fetch` 两种方式调用；
- 已接入 `agentic_workspace` 受限工作区及 7 个文件、代码和 artifact 工具，同样支持两种调用方式；
- 已新增 `benchmark.banking_transfer_and_limit_review` 和 `benchmark.workspace_artifact_delivery` 两道 smoke task；
- 已验证银行任务只完成部分动作时获得中间分，全部原子断言通过时获得 `1.0`，不是简单的全对或全错；
- 通过本地模拟的 OneAPI Chat Completions 端点验证了工具定义发送和工具调用解析；
- 通过 AutomationBench CLI 冒烟验证了任务运行器能够向 API 请求发送任务工具；
- 在 `support.intercom_demo_scheduling` 任务中，第一次请求实际携带了 16 个工具定义；
- 现有评估入口支持 `--max-steps`，正式运行可以显式设置为 50；
- 现有评估结果会保存 `partial_credit`、严格通过结果、断言明细、最终环境状态、工具调用数和性能信息。

## 五、新增的 benchmark 工具

### 1. 银行业务工具

| 工具 | 作用 |
| --- | --- |
| `banking_find_customer` | 根据客户 ID、邮箱或姓名查找客户。 |
| `banking_list_accounts` | 查询客户名下账户及当前限额。 |
| `banking_get_transaction` | 查询交易类型、金额和处理状态。 |
| `banking_search_policy` | 检索本地银行政策。 |
| `banking_verify_identity` | 根据留存信息验证客户身份。 |
| `banking_request_transfer_review` | 为符合条件的转账提交审核请求。 |
| `banking_request_limit_increase` | 提交限额提升申请，不直接修改账户限额。 |
| `banking_transfer_to_human` | 对无法自动完成的事项建立人工转接记录。 |

这组工具可以检查模型是否先查询事实和政策、是否完成必要验证、是否正确区分“提交审核”和“业务完成”，以及是否避免越权直接修改账户状态。

### 2. 受限工作区工具

| 工具 | 作用 |
| --- | --- |
| `agentic_workspace_list_files` | 查看任务提供的虚拟文件。 |
| `agentic_workspace_read_file` | 读取虚拟工作区内的文件。 |
| `agentic_workspace_write_file` | 创建或更新任务交付文件。 |
| `agentic_workspace_run_python` | 在禁止导入、禁止宿主文件访问的受控环境中运行小型数据处理代码。 |
| `agentic_workspace_record_artifact` | 登记交付物类型、大小和检查信息。 |
| `agentic_workspace_inspect_artifacts` | 检查交付物是否存在、非空且大小一致。 |
| `agentic_workspace_finalize` | 仅在交付物检查有效后完成任务。 |

这组工具可以检查模型是否真正读取输入、处理数据、生成文件、保护原始文件并完成可验证交付，而不是只在最终回答中声称“已生成报告”。

两组工具均使用可重置的本地模拟状态，不连接真实银行、不访问宿主文件系统，也不把 benchmark 运行依赖建立在不稳定的外部网络上。它们提升的是工具执行、状态变化和评分闭环的适配性；不会自动补齐 OpenRouter 数据源或多轮用户事件。

## 六、当前评分机制的适配问题

现有 AutomationBench 的默认评分由两部分组成：

- `partial_credit`：通过断言数除以参与评分的断言总数；
- `task_completed_correctly`：所有参与评分的断言都通过时为 1，否则为 0。

这套机制已经比“只看最终一句话”更适合 Agent 任务，因为它直接检查工具执行后的环境状态，而且能保存每条断言的通过或失败结果。

但它不能原样表达当前题库中的 100 分制，原因是：

1. 默认每条断言等权，不能直接表达 40 分、30 分、20 分、10 分的权重；
2. “严重错误时整题最高 40 分”这类硬约束需要单独的 `hard_fail` 或封顶逻辑；
3. T03、T04、T05 这类涉及报告质量、图表质量和结论边界的内容，不能只依靠最终环境状态判断；
4. T07、T08 的中途用户事件不能只靠初始状态和最终状态表达。

建议保留现有评估输出格式，同时在题目断言层增加三类元数据：

| 元数据 | 用途 |
| --- | --- |
| `points` | 将每条原子断言映射到 100 分制中的具体分值 |
| `hard_fail` | 标记泄露密钥、实际退款、误发邮件、违反停止指令等严重错误 |
| `evidence_type` | 标记该项由最终状态、工具轨迹、交付物内容还是教师模型判断 |

最终同时输出：

- `weighted_score`：按题目 100 分制计算的连续分数；
- `partial_credit`：保留 AutomationBench 兼容的归一化部分得分；
- `task_completed_correctly`：严格完成结果；
- `hard_fail_reasons`：严重错误清单；
- `assertion_results`：每条原子断言的结果；
- `trajectory`：完整工具调用和工具返回轨迹。

这样既能接入现有批量 API 测评，又能避免“小遗漏导致整题接近归零”的问题。

## 七、推荐接入方式

### 第一阶段：直接复用现有环境

优先接入 T01 和 T02：

- 使用 `limited_zapier` 工具集；
- 保留每道题的独立初始状态；
- 复用或轻量改造现有 Gorgias 退款任务和 Intercom Demo 排期任务；
- 先验证 OneAPI 在多轮工具调用下的稳定性；
- 记录完整轨迹，而不是只保存最后文本。

### 第二阶段：用现有工具拼装新任务

T05 和 T06 可以优先尝试用现有工具及新增受限工作区搭建：

- T05：受限工作区、Google Drive、Google Sheets、Asana、Slack；
- T06：Asana、Jira、Gmail、Slack；
- 每道题新增独立的 `initial_state`、题面和断言；
- 对未覆盖的业务对象，先用明确的记录字段表示，不要让模型通过最终文字自行“宣称完成”。

### 第三阶段：扩展环境和运行器

T03、T04、T07、T08 仍需要新增或补齐能力：

- T03：旅行预订与保护性预订状态；
- T04：在现有受限工作区之上增加 OpenRouter 录制数据服务，直接在任务对话中提供测试 API Key，并增加 Excel/图表和数据质量检查；
- T07：在现有银行状态和工具之上增加脚本化客户回复；
- T08：在现有工作区和业务工具之上增加中断/恢复事件注入、暂停状态和幂等性检查。

其中 T07 和 T08 不只是新增工具的问题，还需要在 Agent 循环中支持“评估器在指定时机插入新的用户消息”。如果不做这层扩展，就只能把它们改写成一次性任务，题目原本想测的多轮交互和中断恢复能力会消失。

### 推荐的统一运行方式

使用 AutomationBench 运行器，而不是 `model-api-collector`：

```bash
.venv/bin/python -m automationbench.scripts.eval \
  --model "<MODEL_ID>" \
  --base-url "<ONEAPI_BASE_URL>" \
  --api-key-var "<API_KEY_ENV_VAR>" \
  --api chat_completions \
  --toolset limited_zapier \
  --max-steps 50 \
  --max-concurrent 1 \
  --tasks "<TASK_NAME_1>,<TASK_NAME_2>" \
  --export-json "results/agent/<MODEL_ID>-run-1.json"
```

如果某题使用 Responses API，应在同一批次内统一接口类型，并把接口、模型 ID、推理档位、工具集、步数上限和题库版本一并记录。

## 八、最终判断

当前题库的问题不是“题目不能测 Agent”，而是题目和执行环境还没有一一对应：

- T01、T02 已经具备最接近的可运行底座；
- T05、T06 可以利用现有业务工具和新增受限工作区扩展；
- T03 仍需要新的旅行领域模拟环境；
- T04 已具备分析和 artifact 交付底座，但仍缺 OpenRouter 数据源和直接 Key 交接流程；
- T07 已具备银行业务状态和工具，但仍缺完整多轮客户事件；
- T08 已具备可持久化的执行与交付状态，但仍缺中断/恢复事件机制。

所以，最终建议不是把所有题目退回成文本题，而是保留题目的 Agent 目标，并把评估流水线明确拆成：

`模型 API 调用 -> 工具定义 -> 工具执行 -> 环境状态变化 -> 断言/教师模型评分 -> 轨迹归因`

缺少其中任一环节，就只能测到局部能力，不能把结果解释为完整的 Agent 能力。
