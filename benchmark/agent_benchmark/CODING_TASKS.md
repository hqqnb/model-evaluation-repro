# Coding 能力正式候选题库

日期：2026-08-14
版本：2.0

## 1. 使用说明

本文件定义 6 道 Coding 正式候选题。题目统一采用**单文件、一次性交付、空工作区**协议，不再要求模型阅读或修改现有代码库。题目评价模型能否在没有多文件上下文、没有中途澄清和没有外部依赖的情况下，直接完成一个闭合的软件实现：

1. 理解明确的软件需求和输入输出约定。
2. 在一个文件中组织完整的状态、规则、交互和错误处理。
3. 让程序在规定输入和状态下产生正确行为。
4. 处理边界、异常、重复调用和状态恢复。
5. 交付可以由隐藏测试验证、由非技术审核者通过证据卡复核的结果。

六道题不形成对外子能力分。正式结果只展示 Coding 总分、通过题数、题目级失败证据和稳定性。

### 统一单文件交付协议

- 每道题只向模型提供题面、输入输出约定和必要的示例；评测工作区为空，不提供待修改的项目代码库。
- 模型必须在**一次响应中交付一个单一、完整且可运行的文件**。文件名、语言和启动方式由题目明确指定。
- 单文件必须自包含：不得导入、读取、拼接、引用或依赖工作区中的其他文件，不得要求额外的配置文件、资源文件、源码文件或安装步骤。
- 默认禁止联网、CDN、外部服务和未声明的第三方依赖；题面要求的数据必须写入文件、通过标准输入提供，或由评测器通过约定接口注入。
- 模型执行期间**不得向用户提问、请求澄清、要求补充材料或等待用户确认**。遇到题面未覆盖的非关键细节，应采用合理且稳定的默认行为。
- 最终交付只能包含这一个文件的内容。不得同时提交补丁、多文件目录、README、测试文件、运行说明或第二份实现。
- 模型可以在内部进行推理，但评测只保存最终文件和运行结果；不得把“计划、伪代码或解释”当作实现交付。
- 隐藏测试同时检查正常路径、边界条件、错误处理、重复调用、输入替换和资源受限运行。
- 每题保存最终文件、启动结果、隐藏测试结果、运行时间和证据卡。

### 统一评分原则

每题 100 分：

- 核心功能正确性：55 分。
- 边界条件和异常处理：20 分。
- 输入输出、可测试性和结果可复现：15 分。
- 单文件、离线、可运行和交付协议遵循：10 分。

代码长度、注释数量、解释文字、UI 审美和模型自述不进入主分。

### 通用严重失败规则

- 无法安装、构建、导入或启动：本题 0 分。
- 交付多个文件、依赖工作区其他文件、使用网络或未允许的外部服务：本题 0 分。
- 在执行期间向用户提问、请求澄清或等待用户补充信息：本题 0 分。
- 硬编码公开样例且不能处理等价的新输入：相关核心项不得分，并触发题目上限。
- 只提交伪代码、补丁、片段或不能独立运行的代码：本题 0 分。

### 人类证据卡

每道题的评分报告都展示：

- 测试输入或初始状态。
- 预期结果。
- 模型代码实际结果。
- 一句自然语言差异说明。
- 对应需求和得分。

审核者不需要阅读源码，可以通过操作序列、棋盘、牌面、数据表、最终清单或金额结果判断机器评分是否合理。协议类失败单独记录，不用“功能做得好”抵消。

## C01 2048 Roguelike 状态闭环

### 主要区分点

状态机、随机性控制、规则闭环、交互联动和重开清理。

### 交付格式与运行约定

- 交付文件：`solution.html`。
- 运行方式：在无网络的现代浏览器中直接打开，不能依赖 CDN、外部脚本、图片或其他文件。
- 评测器通过页面按钮和 `window.codingApi` 调用实现；文件必须暴露
  `createGame(options)`、`move(direction)`、`setBoard(board)`、`pause()`、`restart()` 和 `getState()`。
- 棋盘、随机数和所有游戏状态必须保存在这一个文件中，不能从工作区读取初始代码或数据。

### 给模型的题面

> 请一次性输出一个单一、完整且可运行的 `solution.html`，实现一个可测试的 2048 Roguelike 游戏状态闭环。不要向我提问，也不要读取或引用工作区中的任何其他文件。核心规则必须可以通过 `window.codingApi` 直接调用，页面只是同一份状态的可视化。
>
> 需要完成：
>
> 1. 实现 4×4 棋盘的左、右、上、下滑移。
> 2. 同一方向的一次移动中，每个方块最多合并一次，合并顺序与标准 2048 一致。
> 3. 有效移动后只生成一个新方块；无效移动不得改变棋盘、分数或随机数状态。
> 4. 支持可注入随机种子，固定种子和操作序列必须得到相同结果。
> 5. 实现两个遗物：
>    - `DoubleStart`：每次新局初始生成两个方块。
>    - `Shield`：第一次本应死亡时消耗遗物并保留当前棋盘，不产生第二次保护。
> 6. 实现分数、遗物、回合数、暂停、死亡、胜利和重开状态。
> 7. 重开后棋盘、分数、遗物、死亡标记和随机序列都必须按新局重新初始化。
> 8. 页面显示必须来自同一个游戏状态，不得单独维护一份会与引擎分叉的展示状态。
>
> 游戏主题、音乐、动效和视觉风格不属于本题要求。优先保证规则、状态和可测试性。

### 隐藏设定

- 公开测试只覆盖简单相邻合并。
- 隐藏测试覆盖：
  - `[2,2,2,2]` 一次向左应得到 `[4,4,0,0]`。
  - 同一移动中生成方块的位置和数值受种子控制。
  - 无效移动不消耗随机数。
  - `Shield` 只触发一次，重开后重新获得。
  - 死亡后不能继续移动或重复结算。
  - 重开不会残留上局最高分、遗物或棋盘。
  - `window.codingApi` 和页面操作得到一致结果。
- 隐藏测试会替换初始棋盘、随机种子和遗物组合，避免只硬编码公开棋盘。

### 目标终态

- 引擎规则、Roguelike 状态和页面状态一致。
- 所有固定输入下产生确定且可复现的结果。
- 死亡、保护和重开形成完整闭环。

|---|---|---:|
| C01-1 | 四方向滑移、合并顺序和得分正确 | 25 |
| C01-2 | 新方块生成、无效移动和随机种子行为正确 | 15 |
| C01-3 | `DoubleStart` 与 `Shield` 真正改变规则 | 10 |
| C01-4 | 死亡、胜利、暂停和重开状态正确 | 15 |

| C01-7 | 单文件启动、按钮操作和约定 API 兼容 | 10 |
| C01-8 | 离线打开、固定种子和重复运行稳定 | 5 |

### 严重失败规则

- 页面能显示但约定 API 无法被直接调用：总分上限 40 分。
- 依赖其他文件、外部资源或等待用户补充信息：本题 0 分。
- 重开残留上一局状态，或死亡后仍可继续改变分数：总分上限 50 分。
- 仅用动画或页面数字伪造规则结果：核心功能不得分。

### 人类结果页

## C02 小丑牌规则与计分状态机

### 主要区分点

规则建模、牌型边界、计分顺序、资源状态机和交互状态一致性。

### 交付格式与运行约定

- 交付文件：`solution.html`。
- 运行方式：在无网络的现代浏览器中直接打开，不能依赖 CDN、外部脚本、图片或其他文件。
- 评测器通过页面按钮和 `window.codingApi` 调用实现；文件必须暴露
  `startRound(options)`、`select(index)`、`unselect(index)`、`play()`、`discard()`、`restart()` 和 `getState()`。
- 牌面、规则、计分、Joker 和回合资源必须保存在这一个文件中，不能从工作区读取代码或数据。

### 给模型的题面

> 请一次性输出一个单一、完整且可运行的 `solution.html`，实现一个可测试的小丑牌规则子集。不要向我提问，也不要读取或引用工作区中的任何其他文件。题目只评价规则、计分和状态，不要求还原原版字体、音效、动画或视觉风格。
>
> 牌型定义如下，按从高到低判断：
>
> 1. 四条：四张牌点数相同。
> 2. 葫芦：三张牌点数相同，另外两张牌点数相同。
> 3. 同花：五张牌花色相同。
> 4. 顺子：五张牌点数连续；A 可作为 1 组成 A-2-3-4-5。
> 5. 三条：三张牌点数相同。
> 6. 两对：两组不同点数的对子。
> 7. 对子：一组对子。
> 8. 高牌：不符合以上牌型。
>
> 还需要完成：
>
> 1. 选牌、取消选牌和出牌，最多选择 5 张。
> 2. 基础筹码按牌型固定为：高牌 5、对子 10、两对 20、三条 30、顺子 40、同花 50、葫芦 60、四条 80。
> 3. 牌型内的筹码为基础筹码加所选牌点数之和。
> 4. 初始倍率为 1，最终分数为 `筹码 × 倍率`。
> 5. 实现两个 Joker：
>    - `Red Joker`：本回合牌型包含对子、两对、三条、葫芦或四条时，倍率加 1。
>    - `Blue Joker`：本回合牌型为同花时，筹码加 20。
> 6. 每回合消耗一次出牌机会；弃牌只消耗弃牌次数，不结算分数。
> 7. 回合结算、资源扣减、失败和重开必须保持一致。

### 隐藏设定

- 常见错误实现包括：
  - 一张牌被误判为同花。
  - 选牌取消后仍参与计分。
  - `Red Joker` 只改变页面文字，没有改变实际分数。
  - `Blue Joker` 与倍率修改顺序错误。
  - 重开后保留上回合的 Joker 或剩余次数。
- 隐藏测试覆盖：
  - 同花与顺子同时成立时按题目规定使用同花。
  - A-2-3-4-5 是顺子，Q-K-A-2-3 不是顺子。
  - 重复点数不能被识别为顺子。
  - 选中 4 张、取消 1 张后只计算 3 张。
  - Joker 的生效条件、分值和资源变化。
  - 失败后不能继续出牌或重复结算。
- 隐藏测试会替换牌面、花色、资源和 Joker 组合。

### 目标终态

- 牌型识别、计分明细、Joker 效果和资源状态在引擎与页面中一致。
- 所有牌型边界都有明确结果。
- 出牌、弃牌、失败和重开不会重复改变状态。

### 计分项

| ID | 可验证要求 | 分值 |
|---|---|---:|
| C02-1 | 八类牌型识别和优先级正确 | 25 |
| C02-2 | 选牌、取消选牌和出牌状态正确 | 10 |
| C02-3 | 基础筹码、倍率和最终分数正确 | 15 |
| C02-4 | 两个 Joker 的条件和实际效果正确 | 10 |
| C02-5 | 回合资源、弃牌、失败和重开正确 | 15 |
| C02-6 | 牌型边界和重复操作不会重复计分 | 10 |
| C02-7 | 单文件启动、牌面展示和约定 API 兼容 | 10 |
| C02-8 | 离线打开和固定牌局测试稳定 | 5 |

### 严重失败规则

- 页面展示的牌型或分数与约定 API 返回的规则结果不一致：核心功能不得分。
- Joker 仅显示说明而没有改变真实结算：对应功能项不得分。
- 重开后资源或 Joker 残留：总分上限 50 分。
- 依赖其他文件、外部资源或等待用户补充信息：本题 0 分。

### 人类结果页

展示牌面、选中牌、识别牌型、基础筹码、倍率、Joker 变化、最终分数和回合前后资源。审核者可以用牌面和公式直接复核结果。

## C04 家庭采购清单同步缺陷修复

### 主要区分点

状态建模、事件顺序、幂等处理、错误隔离和结果兼容。

### 交付格式与运行约定

- 交付文件：`solution.py`。
- 运行方式：`python3 solution.py`，通过标准输入接收 JSONL 请求，并向标准输出返回 JSONL 结果。
- 评测器会在同一进程中多次调用约定入口 `handle(request)`；实现也必须支持独立命令行运行。
- 所有状态、幂等记录和错误结果必须由这一个文件管理，不能导入、读取或引用工作区中的其他文件。
- 不要求兼容任何未在题面声明的旧代码；输入输出协议以本题定义为准。

### 给模型的题面

> 请一次性输出一个单一、完整且可运行的 `solution.py`，实现家庭采购清单同步服务。不要向我提问，也不要读取或引用工作区中的任何其他文件。
>
> 两台设备可能在离线状态下分别记录操作，恢复连接后把操作日志交给服务端。操作格式为：
>
> `{"op_id", "device_id", "item_id", "kind", "quantity", "timestamp"}`
>
> 其中 `kind` 为 `add`、`set` 或 `remove`。
>
> 同步规则：
>
> 1. 同一个 `op_id` 重放多次只能生效一次。
> 2. 两台设备对同一商品分别执行 `add` 时，数量相加。
> 3. `set` 和 `remove` 按时间戳决定先后；时间戳相同时，`device_id` 字典序较大的操作生效。
> 4. 同步请求中操作顺序不可靠，不能假设日志已经按时间排序。
> 5. 数量不得小于 0；非法操作返回明确错误，不得污染其他商品。
> 6. 同一个同步请求整体重试时，已成功的操作不得再次生效，未成功的合法操作仍需继续处理。
> 7. `handle(request)` 的输入输出结构和命令行 JSONL 格式必须严格遵循本题约定。
>
> 请定位根因并修复，不要只针对公开样例增加特殊判断。

### 隐藏设定

- 常见错误实现包括：
  - 幂等键只在单次请求内记录，跨请求重试会重复累加。
  - 合并逻辑依赖输入顺序，乱序日志会产生不同结果。
  - `remove` 后较旧的 `set` 会错误恢复商品。
  - 某一条非法操作会提前终止整个批次。
  - CLI 的错误字段和题面约定的返回结构不能改变。
- 隐藏测试覆盖：
  - 两设备离线 add、乱序提交和整批重试。
  - 同一商品的 set/remove 时间冲突。
  - 部分合法、部分非法的批次。
  - 空清单、重复删除、数量为 0 和极大数量。
  - 多次同步后最终结果和单次同步一致。
- 测试会使用新的商品 ID、设备 ID、操作 ID 和时间戳，不能依赖固定样例。

### 目标终态

- 相同的有效操作集合无论提交顺序和重试次数如何，得到同一个最终清单。
- 非法操作不会污染其他商品或阻断整个批次。
- `handle(request)`、CLI 输出和单设备行为保持兼容。

### 计分项

| ID | 可验证要求 | 分值 |
|---|---|---:|
| C04-1 | add、set、remove 的冲突规则正确 | 20 |
| C04-2 | 操作乱序时仍得到正确最终状态 | 10 |
| C04-3 | 跨请求和整批重试保持幂等 | 15 |
| C04-4 | 非法操作隔离且批次可继续处理 | 10 |
| C04-5 | 空值、重复删除、零数量和极端数量处理正确 | 15 |
| C04-6 | `handle(request)`、CLI 和 JSONL 协议兼容 | 15 |
| C04-7 | 数据不会因异常操作进入负数或不一致状态 | 10 |
| C04-8 | 在限定输入规模下运行时间和内存稳定 | 5 |

### 严重失败规则

- 修改题面约定的入口、CLI 参数或输出协议：总分上限 50 分。
- 只处理示例 ID 和示例操作序列，无法处理替换后的输入：核心功能不得分。

- 依赖其他文件、外部资源或等待用户补充信息：本题 0 分。

### 人类结果页

## C05 活动报名、候补与通知功能

### 主要区分点

状态迁移、资源容量、通知一致性、快照恢复和部分失败处理。

### 交付格式与运行约定

- 交付文件：`solution.py`。
- 运行方式：`python3 solution.py`，通过标准输入接收 JSONL 请求，并向标准输出返回 JSONL 结果。
- 评测器会在同一进程中多次调用约定入口 `handle(request)`；实现也必须支持独立命令行运行。
- 活动、报名、候补、通知和重试状态必须由这一个文件管理，不能导入、读取或引用工作区中的其他文件。
- 评测器通过请求中的 `state` 模拟进程重启，不要求模型实现外部持久化。

### 给模型的题面

> 请一次性输出一个单一、完整且可运行的 `solution.py`，实现“容量限制、候补队列和报名通知”功能。不要向我提问，也不要读取或引用工作区中的任何其他文件。
>
> 规则如下：
>
> 1. 活动有固定容量；确认报名人数不能超过容量。
> 2. 满员后新用户进入候补队列，候补顺序按进入时间；同一用户不能重复进入。
> 3. 已确认用户重复报名必须幂等，不得重复占用名额或发送重复确认。
> 4. 已确认用户取消后，候补队列第一位自动递补为确认报名。
> 5. 取消候补用户只移除其候补状态，不影响确认报名。
> 6. 每次状态变化产生一条通知事件；同一状态变化重试不得重复发送。
> 7. 通知发送失败时，报名状态仍需保持正确，通知事件进入可重试的待发送队列。
> 8. `handle(request)` 返回的确认名单、候补名单和通知状态必须能反映真实状态。
> 9. 输入输出字段必须保持本题约定，不得通过省略字段规避检查。

### 隐藏设定

- 常见错误实现会在报名状态和通知状态之间产生不一致，例如“名额已占用但名单没有人”。
- 通知模块可能在发送后超时，重试时不能重复产生状态变化。
- 隐藏测试覆盖：
  - 容量为 0、1 和大于参与人数。
  - 重复报名、重复取消和同一用户在确认/候补之间转换。
  - 取消确认用户后只递补一个候补。
  - 候补通知失败后重试，不重复递补。
  - 通过请求中的 `state` 恢复名单、候补顺序和待发送事件。
  - `handle(request)` 和 CLI 字段保持兼容。
- 测试会替换活动 ID、用户 ID、容量和通知失败位置。

### 目标终态

- 活动容量、确认名单、候补顺序、取消结果和通知队列始终一致。
- 重试只补偿未完成的通知，不重复改变报名状态。
- `handle(request)` 和 JSONL 读取方式继续可用。

### 计分项

| ID | 可验证要求 | 分值 |
|---|---|---:|
| C05-1 | 容量限制和确认报名正确 | 15 |
| C05-2 | 候补顺序、重复报名和取消行为正确 | 20 |
| C05-3 | 取消后只递补一名并保持状态一致 | 15 |
| C05-4 | 通知事件准确且可幂等重试 | 15 |
| C05-5 | 通知或持久化部分失败后状态可恢复 | 10 |
| C05-6 | 状态快照恢复后名单、候补和待发送事件正确 | 10 |
| C05-7 | `handle(request)`、CLI 和数据字段兼容 | 10 |
| C05-8 | 多用户高频操作下不产生超容量或重复记录 | 5 |

## C06 购物车结算引擎

### 主要区分点

规则建模、优惠组合、结构化输出、隐藏输入泛化和性能约束。

### 交付格式与运行约定

- 交付文件：`solution.py`。
- 运行方式：`python3 solution.py`，通过标准输入接收一个 JSON 请求，并向标准输出返回一个 JSON 结果。
- 评测器会在同一进程中多次调用约定入口 `calculate(request)`；实现也必须支持独立命令行运行。
- 所有结算规则、金额处理和输出逻辑必须由这一个文件完成，不能导入、读取或引用工作区中的其他文件。

### 给模型的题面

> 请一次性输出一个单一、完整且可运行的 `solution.py`，实现购物车结算引擎。不要向我提问，也不要读取或引用工作区中的任何其他文件。
>
> 输入包含：
>
> - 商品：`sku`、`category`、`unit_price`、`quantity`。
> - 活动规则：满减、买赠、分类折扣和优惠券。
> - 结算选项：是否包含赠品、是否按元四舍五入。
>
> 输出必须包含：
>
> 1. 每个商品行的原价、小计、折扣和最终金额。
> 2. 每条优惠规则实际是否生效以及折扣金额。
> 3. 赠品明细。
> 4. 商品行最终顺序。
> 5. 总折扣和应付金额。
>
> 输入输出结构、金额类型和错误格式必须严格遵循本题约定。不要把公开样例写成特殊分支。
>
> 实现必须支持至少 100,000 个商品行，在隐藏数据上满足时间和内存限制。

### 规则约定

- 订单行按输入顺序输出；相同 SKU 不自动合并。
- 商品小计为 `unit_price × quantity`，金额使用十进制定点计算，不使用二进制浮点近似。
- 分类折扣先于优惠券；满减门槛按折扣前商品总额判断；同一类优惠按题面给出的顺序处理。
- 买赠只产生赠品明细，不改变付费商品行金额；赠品数量按完整购买组数计算。
- 任何非法输入都返回结构化错误，不得输出部分伪造的成功结果。

### 评分方隐藏设定

- 隐藏测试重点覆盖：
  - 多条优惠同时满足时的实际叠加顺序。
  - 满减门槛使用原价还是折后价。
  - 买赠商品是否计入门槛和输出顺序。
  - 分类折扣与优惠券的互斥关系。
  - 金额恰好处于门槛、0.01 元边界和需要舍入的场景。
  - 商品输入乱序、重复 SKU、零数量和非法金额。
  - 100,000 行输入的时间和内存。
- 隐藏测试会使用公开样例之外的新 SKU、类别、价格和规则组合。
- 隐藏测试会检查输出行顺序、折扣归因和总金额，不接受只返回一个总价。

### 目标终态

- 对未见过的商品、价格和优惠组合，按题面规则输出正确的结构化结果。
- 金额、折扣归因、赠品和行顺序都正确。
- 大规模输入在限定资源内完成。

### 计分项

| ID | 可验证要求 | 分值 |
|---|---|---:|
| C06-1 | 基础商品、小计、总价和输出结构兼容 | 20 |
| C06-2 | 单规则和多规则组合实现正确 | 20 |
| C06-3 | 折扣归因、赠品和行顺序正确 | 10 |
| C06-4 | 门槛、舍入、重复 SKU、零数量和非法输入正确 | 15 |

| C06-6 | `calculate(request)`、CLI 和错误格式兼容 | 10 |
