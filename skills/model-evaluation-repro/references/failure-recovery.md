# 失败诊断与恢复

## 先分类

按以下顺序诊断：

1. 密钥不存在或鉴权失败；
2. model ID/endpoint 不存在；
3. 协议转换或参数不兼容；
4. 图片或工具 schema 未正确发送；
5. 网络、超时、429、5xx、瞬时上游 404 或断流；
6. 收到 HTTP 200，但响应为空、半截或没有可见文本；
7. API 成功，但答案错误或 Coding/Agent 没有形成交付。

只有第 7 类才主要进入能力与评分判断。前六类先按技术问题处理。

## 恢复原则

- 保留失败请求、响应头、错误体、attempt 记录和时间。
- 同一逻辑请求内部的传输重试不计为新的独立样本。
- 只重试明确的瞬时错误；确定性参数转换错误先改配置。
- 非流式长请求超时或返回不完整时，优先测试流式。
- 某协议转换失败时，可测试 Provider 已支持的另一个兼容协议。
- 切换协议或流式时保持题面、模型 ID、温度和最高推理强度不变。
- 模型仍持续输出时不要人工截断；等待 `stop`/`[DONE]` 或明确失败。
- 复用历史成功结果前，核对题面哈希、模型、推理强度、协议和素材一致。

## Coding 特殊情况

`finish_reason=stop` 但回答仅包含 `execute_bash`、`fs_write` 等工具调用请求时：

1. 标记为“API 完成、交付物未形成”，不能直接给 Coding 完成分。
2. 若当前运行支持工具，继续执行调用并把结果回传模型。
3. 保存每轮模型响应、工具请求、工具结果和 workspace。
4. 直到项目文件真实存在、模型结束且能够启动。
5. 若模型原始版本不能启动，评分按原始版本；评测侧修复只能另存并标注。

## 新旧结果冲突

使用以下判定：

- 新运行成功且证据完整：可替代旧“限流/空响应/未收到图片”结论。
- 新运行只到 API 成功：不能替代旧评分，需要继续内容或交付物复核。
- 旧文件为 0 字节：只说明那一次失败，不说明模型始终无回答。
- 文档与本地冲突：先核 run ID、日期、模型、题目和内容，再提出拟修订，不直接覆盖。

## 回填措辞

不要把技术故障写成模型能力：

- 正确：`未发生模型调用或工具操作，未形成任务交付；不应归因于 API 限流。`
- 正确：`请求成功并收到完整回答，但未形成可运行代码。`
- 错误：没有证据时写“模型不会”“未收到图片”或“因限流未完成”。
